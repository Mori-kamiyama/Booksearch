# ローカルとAWSのスキャン処理の差分

以下は修正前の差分調査。対応後の方針は末尾の「共通化と中央棚の読み取り」を参照。

2026-10-02調査。対象はローカル実験CLI `scripts/build_book_catalog.py` と `src/{detection,ocr,lookup,video}.py`、`scripts/shelf_locator.py`、稼働中のYOLO/lookup/OCR/優先OCR Lambda。
このチャットで作成した未デプロイ修正を、既存の差分・原因として数えない。

## 確認方法

Lambdaの実コードを取得。YOLO/lookupはAWSが参照するイメージdigestとローカルDockerのRepoDigestsを照合して、停止状態のコンテナからhandlerとassetsを取り出した。OCR2種はLambda配布zipから取得。4種すべてのhandlerはGit HEADとバイト一致。
本番コード変更、Lambda起動、OCR API要求、既存データ更新は行っていない。
本番参照イメージをローカルで起動したのはパッケージ版の読み取りだけ。

### 行動比較

- 最新フレーム`63104327974d...`でローカル品質関数を実行し、中央2棚を保持、下棚を`too_small`で除外。ぼけ指標はAWS保存値と一致。
- 同フレームのタグ角度は約-1.5〜3.4度。棚割当は既存のローカル/AWS方式ともr05/r04/r03で一致した。象限差は今回の原因と断定しない。
- 90度のタグ軸を使う人工入力では、同じ点がローカル`top_right`、AWS`bottom_right`になることを確認。向き検査でmismatchとなるタグは両方スキップするため、実影響はmapのexpected_angle設定にも依存する。
- 同じ本番DBに`プログラミング TypeScripx`を入力。ローカルは「プログラミングTypeScript」をscore0.9412で返し、本番lookup関数は0候補。

## 一致している部分

- YOLOの重み、data側のAprilTag map、known_books、本番lookup同梱DBと手元lookup同梱DBはSHA-256一致。
- YOLO既定imgsz640、confidence0.25、crop余白2%、JPEG品質92、boxの並べ方は同じ。
- OCRモデルは`gemini-3.1-flash-lite-preview`。元のOCRプロンプトはローカル・本番通常・本番優先で同一。
- 書名正規化と文字スコア式、採用閾値0.72/auto0.85は同じ。
- 著者・出版社でも一致させる挙動は**修正前は両方に存在**する。AWSだけの移植差ではない。
- 冊数を複数フレームのbooks合計で数える挙動も**修正前は両方に存在**する。
- cropのhash計算は両方8×8 aHash。同一hashでも重複の採用条件が異なる。

## 限界・優先順位

旧ローカル実験で使った全てのCLI引数・出力・入力解像度は残っていない。現コードの既定と実行環境の比較であり、過去の全実験の再現ではない。
ローカルCLIの既定DBパス`outputs/library/library.db`は現在存在しない。明示指定しなければ照合されない。今回の照合比較は同じ本番同梱DBを両方へ渡してデータ差を排除した。

1. 品質判定は、ローカルで通す/落とす実画像を基準に解像度相対の閾値を校正する。80pxへの単純な緩和は戻す候補。
2. 棚の象限と距離制限の意味を統一し、傾いたタグの画像で比較する。
3. 書名検索の検索範囲を統一するか、AWSで全件類似検索を省く意図と精度への影響を明示する。
4. 動画入力とlive入力の選別・重複条件を別々に評価する。全条件を無条件にローカルへ合わせない。
5. 認識ロジック・設定の共通化または同一入力での差分テストにより、実験の改善がAWSへ伝わる仕組みにする。

先の未デプロイ修正は別に残っている。特に画面端の追加規則とAWS限定の書名照合変更は、既存差分の整理を踏まえて必要性・共通化方針を見直す。

## 共通化と中央棚の読み取り

### 分岐した経緯

2026-06のAWS向け移植でローカルとLambdaの認識コードが分かれ、低解像度対応・棚投票の競合・配送とOCR再利用の修正がAWS側で進んだ。ローカルにも個別の検索・タグ座標処理が残り、どちらが基準かを決める差分テストがなかった。HEADと本番のhandlerは一致しており、今回の差分はデプロイ漏れではない。

### 今回の対応

- `aws/functions/shared/scan_core.py`を品質、タグ座標、OCRプロンプト/解析、OCR書名照合の共通実装とした。ローカルの`src/scan_core.py`は同じ実装のimportアダプタ。SAMのOCR通常/優先ビルドと両Dockerイメージに同じsharedを含める。
- crop短辺の下限を画像短辺の28%（最低80px）へ相対化。ぼけ50、端+縦横比除外はAWSの既存条件を保持。ローカルCLIから絶対pxの明示指定もできる。28%は今回の入力で中央棚と小口を区別する暫定値であり、多様な棚で校正済みではない。旧実験の全入力は残っていない。
- 先に足した画面端6%の特殊規則は撤回。共通のサイズ判定で今回の入力を除外する。
- タグの向きを使う象限判定を共通化。距離上限はAWSの対角線方式を採用。AWSのnearest vote/競合記録は保持。別辞書で検出した同IDを誤ってmapへ当てないよう指定辞書だけを使う。
- OCR書名検索はローカルの全蔵書への類似検索を両側へ導入。著者・出版社だけのOCR一致は除外。検索画面向け一般検索は従来の著者/ISBN検索を保持。
- 候補スコア差が0.08未満、または書名長の一致率が65%未満ならautoにしない。部分読み取りは候補全てをreviewにする。OCRの自己申告clearだけで正しさを保証しない。
- AWSの棚/IoUを考慮する重複判定、claim、transaction、outboxは保持。永続fingerprintのscopeへ共通POLICY_VERSIONの`scan-v2`を加え、古いOCRを新方針の結果として再利用しない。旧cacheは削除しない。
- 通常/優先OCRとローカルで同じプロンプトとtemperature=0を使う。小さい日本語の副題も読むよう明示し、部分読み取りを記録する。
- 自動確定していない蔵書候補の名前・表紙でOCR文字を置き換えないよう、live画面と結果画面を調整。要確認候補は棚の確定観測に使わない。
- ライブの冊数は棚別に確定ID/正規化タイトルを一意集計する。同名複本や誤読による揺れがあるため物理冊数の保証はない。

### 中央2棚の実OCR比較

S3の実crop2枚を本番と同じ`gemini-3.1-flash-lite-preview`で再OCRした。結果は本番DynamoDB/S3へ登録していない。

1. 推測禁止だけを強調: 下棚の14エントリ中5件が「JavaScript」のみとなった。clearの自己申告でも副題が欠けた。安全寄りの指示だけでは読み取りの情報量を落とす。
2. HIGH media resolution: 同じ2枚で返るタイトルは上記と同等。今回の取りこぼしを解消しなかったため既定変更しない。APIの[設定仕様](https://ai.google.dev/gemini-api/docs/media-resolution?hl=en)を確認した。
3. 下棚を重なる左右2領域へ分割: 一部の副題を拾うが重複/揺れも生じる。通常処理には採用しない。
4. Gemini 2.5 Flashで比較: 下棚では一部を拾うが上棚の副題を落とし、全体の改善と判断できないためモデル変更しない。3 Flash Previewは504になり比較未完。
5. 小さい日本語の副題を省略しないよう指示を追加: 下棚で「いちばんやさしいJavaScriptの教本第2版」「知識ゼロからのJavaScript入門」「JavaScript逆引きレシピ第2版」などを返した。14エントリの「JavaScript」だけの出力は0件になった。ただし、例えば第3冊の書名の誤読や上棚の補完/誤読が残る。詳しくなったことと正しいことは区別する。

各結果は`/tmp/booksearch-parity-audit/central-*.json`に保存。暫定的な比較で、正解書名を全冊に付けた精度評価ではない。特に未認識だった本をユーザーに確認し、画像根拠の正解集合を増やす。

### ユーザーが確認した取りこぼし2冊

- 「図解！JavaScriptのツボとコツが絶対にわかる本」: 同梱DBのID748、正式表記は「図解!JavaScriptのツボとコツがゼッタイにわかる本」。通常向きの棚画像では調整後も「図解！JavaScript超入門」となり、小さい日本語が抜ける。この文字列に最も近い候補は別の「JavaScript『完全』入門」なので、自動確定を許さずreviewにする。正しい全文を入力すればユーザー表記でもscore0.8889でID748に照合する。
- 「確かな力が身につくJavaScript超入門」: ID2131。調整後の通常向きOCRで書名を読め、対応する候補へ照合。ただしOCRの付加した「第2版」は蔵書DBの書名にないため、版の特定まで検証できたわけではない。

同じモデル・プロンプトへ棚cropを90度回転して渡すと、2回の実行で上記2冊の書名全文を読めた。「図解！…」の1冊だけ切り出した画像でも全文を読める。文字が元画像に存在しないのではなく、棚全体の縦書きの小さな文字を落とすことがこの本の原因と考える。

ただし上棚を回転すると架空の副題や重複が増えた。元画像と回転画像の2枚を同時に渡しても「図解！…」は省略された。縦書きを一文字ずつ読む指示の追加でも省略は残る。これらの方式を無条件に通常処理へ採用しない。2冊の照合と、省略したタイトルから別の本を自動確定しないことを回帰テストに追加したが、通常処理での「図解！…」全文読み取りは未解決。今後は画像内の位置を保った背表紙単位の再読などを評価する必要がある。

実験結果は`user-target-ocr.json`、`central-shelves-two-view-ocr.json`、`central-shelves-rotation-repeat-ocr.json`、`central-shelves-vertical-prompt-ocr.json`（上記/tmpディレクトリ）。原画像の切り出し・再JPEG化を伴う比較であり、向き以外の影響を完全に排除した評価ではない。

### 検証

AWS系・共通方針・ローカル永続fingerprintのPython回帰81件成功（ユーザー指定2冊の4ケースを含む）。フロント単体59件成功、フロント型検査/buildとSAM lint成功。結果画面の探索対象状態のブラウザ回帰5件成功。
品質は画像0.5倍/1倍/2倍で同じ採否、タグ回転、誤字検索、部分読み取りのauto抑制、共通OCRプロンプトを回帰対象にした。
本番の依存を保持したYOLO/lookupのパッチイメージをビルド。YOLOコンテナ内で実画像の中央2棚がtrue・下棚がfalse、lookupコンテナ内でTypeScripxの誤字を正しい候補へ照合できることを確認。OCR通常/優先のSAM artifactをビルド。

既存の幻覚観測は残っている。誤観測の清掃や完了済みjobの置換は、対象を選んで別途実施する必要がある。
