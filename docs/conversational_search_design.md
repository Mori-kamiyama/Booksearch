# 対話型検索の再設計案

> 状態: 独自AI検索はユーザー判断で取り下げ。画面・入口・開発プロキシを撤去し、ローカルAIサーバーも停止。以下は試作時の記録で、現在のアプリ仕様ではない。検索ロジックは検証資料として保持し、ChatGPT接続は未実装。

調査日: 2026-09-28。設計案であり、この文書の作成時点では検索ロジックを変更していない。

## 今の問題と設計判断

現実装のプロンプトは「もっと薄い」など数値が不明なら具体的な上限を確認するよう指示している。これは厚さを知りたい利用者には使えるが、読書負荷を下げたい利用者をページ数の回答へ誘導してしまう。また、確認質問と検索結果が排他的で、質問と暫定候補を同時に出せない。履歴はあるが、目的・確定条件・柔らかな好み・未確定の解釈を整理していない。

目指すのは、利用者が言い方や方針を変えながら目的に合う本へ近づける対話。最初から属性を順に埋める形式にしない。主題を知るだけでなく、その本を何に使いたいかを理解する。ただし全員に目的を聞くのではなく、誤解すると候補が大きく変わる場合に質問する。

## 調査で確認した原則

- Microsoft HAX G10は、利用者の目的が不明確な場合に曖昧性を解消したり、支援範囲を限定したりする設計を推奨する。G9は訂正しやすさを重視する。[G10](https://www.microsoft.com/en-us/haxtoolkit/guideline/scope-services-when-in-doubt/)、[G9](https://www.microsoft.com/en-us/haxtoolkit/guideline/support-efficient-correction/)
- Googleの会話設計は、利用者に決まった言い方を学ばせず自然な表現に対応すること、選択肢を回答の全範囲と見せないこと、1度に1つの質問を推奨する。[Commands](https://developers.google.com/assistant/conversation-design/commands)、[Questions](https://developers.google.com/assistant/conversation-design/questions)、[Chips](https://developers.google.com/assistant/conversation-design/chips)。音声向け・旧Assistant系の資料なので、チャットUIの最適解を実証したものとは扱わず、会話原則を参考にする。
- Google PAIRは、フィードバックを受けたら反映し、いつ何が変わるか利用者に分かるようにすることを重視する。[Feedback + Control](https://pair.withgoogle.com/chapter/feedback-controls/)
- AliannejadiらのCIKM 2021論文は、質問を先にする戦略と候補を出してから調整する戦略の比較で、常に優位な組み合わせはないと報告する。質問の負担や初回検索の質によって戦略が変わる。49のTRECトピックを使った分析であり、この蔵書UIに直接同じ効果を保証しない。[論文](https://arxiv.org/abs/2109.05955)
- InSCItは、人同士の情報探索で、直接回答・確認質問・関連情報の提示を状況に応じて使う対話を扱う。応答形式を1種類に固定しない設計の参考になる。[TACL 2023](https://direct.mit.edu/tacl/article/doi/10.1162/tacl_a_00559/116048/InSCIt-Information-Seeking-Conversations-with)

以下はこれらを踏まえたこのアプリ向けの仮説・提案であり、検証済みの製品効果ではない。

## 応答を決める流れ

1. 最新の発言を、前の質問への回答だけでなく、目的変更・訂正・条件の追加/解除・比較依頼として解釈する。質問への直接回答がないことをエラーにしない。
2. 主題、利用目的、知識/経験、明示した必須条件、柔らかな好み、未確定の解釈を更新する。更新根拠の利用者発言を保持する。
3. 候補が大きく変わる曖昧さかを判断する。必要なら軽い蔵書検索で候補の分かれ方を確かめる。
4. (a)意味が十分明確なら検索、(b)目的が分岐するなら短い質問1つ、(c)候補を見れば好みを言いやすいなら異なる2〜3冊と任意の質問を出す。
5. 利用者の反応で更新。不要になった質問は捨て、答えていない属性を全部埋めようとしない。

質問基準は「この回答で推薦する本が変わるか」「利用者が今答えられるか」「候補を見せるほうが楽ではないか」。数値化した不確実性の閾値は現段階で導入しない。

## 具体例

### 英語の本

利用者: 英語の本を読みたい。
応答例: どんなふうに使いたいですか？ 英語の勉強、英語での読書、デザインの参考など。
候補ボタン: 英語を学ぶ / 英語で読む / デザインの参考。自由入力は常時有効。

「英語」という主題を英語学習と確定しない。資料の言語と対象分野と利用目的を分ける。利用者が「デザインの例として」と答えたら語学レベルを聞くのではなく、表紙・文字組み・レイアウトなど、必要ならデザインの観点を絞る。すでに利用目的が明確な質問には同じ確認をしない。

注意: 表紙画像から中面のレイアウトや読みやすさは保証できない。紹介文や利用できる見本に根拠がなければ、デザイン資料としての適合性は未確認と伝える。本文言語も書誌上で確認できる範囲に限る。

### ページ数質問への「簡単め」

AI: 何ページ以下がよいですか？
利用者: ページ数より簡単めがいい。
望ましい応答: 読みやすさを優先して探します。前提知識が少なくて済む本を中心に見てみます。

未回答のページ数質問は取り下げ、200ページ以下などに変換しない。「簡単め」をその分野の入門・前提知識・説明の形式に関する希望として扱う。今までに明示された300ページ以下という制限がある場合は、「簡単め」だけで勝手に解除しない。「ページ数は気にしない」なら解除する。

短い本と易しい本は異なる。現カタログでlevelが付いた本は31冊と少ないので、beginnerのハードフィルターを機械的に適用しない。内容紹介の対象読者や前提知識の根拠から優先し、不明を断定しない。

### 曖昧な「薄い」

候補のページ数が分かる場合、現在の候補より短い本を優先して仮提示する方法もある。「冊子として薄い」「短時間で読める」「内容が軽い」のどれかが大きな分岐になる場合は「読み切りやすさと内容のやさしさ、どちらを重視しますか？」等を1問だけ聞く。必ず数値を入力させるルールにはしない。

## 最小限の実装案

- 数値フィルター用の実行側検証と根拠IDの検証は維持する。
- 会話の解釈を管理する状態を追加する。目的、主題、好み、明示条件、保留中の質問を分け、利用者の原文に紐づける。初期版は少数の項目と自由文でよく、巨大な分類体系は不要。
- 明示条件だけ除外フィルターに使い、柔らかな好みは順位や候補比較に使う。推測は利用者の確定条件に昇格させない。
- 返却形式を `message + books + optional_question + suggestions + active_preferences` にし、質問と本を共存可能にする。
- 応答文では「何を理解し、何を変えたか」を短く示す。書籍の事実・推薦根拠はカタログに紐づく情報だけを表示する。
- 選択肢は入力の補助。選択肢と違う「簡単め」「やっぱりデザイン用」も受理し、次の行動を再計画する。
- UIではページ数入力を初期状態から常設する必要はない。必要なときの補助とし、目的・好みは短く訂正可能に表示する。

## 実装前に固定する評価会話

1. 英語の本 → デザイン用（英語学習と決めつけない）。
2. 英語の勉強 → ページ数質問 → 簡単め（数値の再質問をしない）。
3. Python経験あり → 初歩は不要（一般的入門書ばかり出さない）。
4. Python/300ページ以下 → もっと簡単（ページ上限は保つ）。
5. Python/300ページ以下 → ページ数は気にしない（上限を解除）。
6. もっと薄い → おすすめでいい（任意の質問を強制しない）。
7. 何となく探している（対照的な少数候補から反応をもらう）。
8. 2冊目みたいな本（前の候補を参照し、根拠を確認して再検索）。
9. 学習用 → やっぱり装丁の参考（目的を変更、以前の学習条件を再検討）。
10. 該当なし（無関係な本を埋め草で返さず、条件緩和を提案）。

測るもの: 上位候補の目的適合、訂正が次のターンへ反映された割合、不要な再質問、明示条件違反、候補に辿り着くターン数、待ち時間。会話が続くことやクリックだけを成功としない。まず固定会話と人の評価で比較し、ユーザーシミュレーションだけで品質を保証しない。

## 今回の試作範囲

事前定義したReactの選択カード・書籍カード・比較表を組み合わせるGenUIを実装した。ページ数質問を必須にせず、自由入力による目的変更と候補への任意質問を許す。モデルは表示種別と確認質問を返し、書籍と根拠は既存のID検証を通す。詳細と実測の限界は `ai_search_local.md` に記載。目的・好みの構造状態、上記10会話すべての実モデル評価は未完了。
