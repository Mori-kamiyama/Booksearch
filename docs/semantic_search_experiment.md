# 意味検索のローカル比較

## 方針

約4,200冊の段階では新しい検索サーバーを作らず、既存のカタログを読み取り、Bedrockのベクトルと再順位付けを比較する。書名・ISBNの完全一致とハードフィルターは優先する。今週のおすすめ、公開API、UIは変更しない。

試作は `scripts/evaluate_semantic_search.py`。Cohere Embed Multilingual v3で書名・著者・確認済み内容紹介・テーマの日本語ラベルを埋め込み、ローカルで全件コサイン比較する。AND/別名検索との順位をRRFで統合し、最大30冊をCohere Rerank 3.5に渡す。文字列・モデル・用途をキーにベクトルを保存し、途中停止後も再利用する。埋め込み失敗はキーワード、Rerank失敗は統合結果へ戻し、レポートに失敗を明示する。

## 確認できたことと未検証部分

- 4,202冊、内容紹介3,380冊を読み込める。入力DBは閉じた生成物を読み取り専用で扱う。
- `tests/fixtures/semantic_queries.json` に25件。自然文、完全一致、C++/C#、誤字、無意味な文字列、ページ数・レベル・テーマの条件を含む。
- 制約維持、完全一致優先、重複排除、障害時の代替、次元不一致などのローカルテスト7件が成功。
- 2026-09-28の短文1件ずつの呼び出しでは、CohereとTitanの両方が `AccessDeniedException: Your account is currently being verified`。AWSのメッセージは通常2時間未満としているが、解除は未確認。
- 全カタログの送信実行は自動承認レビューに拒否された。書名・著者・内容紹介・テーマの送信と従量課金の明示承認待ち。全カタログは未送信。実モデルの精度・待ち時間は未評価。

ローカルのキーワード比較はAPIの並び順やフロントエンドの誤字補正を完全には再現しない。したがって現行UIとの差は別途実際のAPI/UIでも確認する。意味検索は無関係な文字列にも最近傍を返すので、そのまま公開検索には使わない。関連性の閾値はモデル実測と人手評価から決める。レベル不明を初心者と推測しない。1冊2,000文字で切り詰め、モデル側の512トークン上限でも末尾を切るため、長い日本語紹介文の情報落ちを評価する。

## 実行

AWS送信なしの準備（実施済み）:

```sh
uv run --no-project python scripts/evaluate_semantic_search.py \
  --db outputs/discovery-language/library.db --output outputs/semantic --prepare-only
```

送信・課金の承認とAWS利用制限の解除後に実行するコマンド:

```sh
uv run scripts/evaluate_semantic_search.py \
  --db outputs/discovery-language/library.db --output outputs/semantic
```

新規キャッシュなら埋め込みは最大4,202冊＋25検索文、Rerankは最大25回（各最大30冊）。最初に短文を1件だけ呼び出し、拒否時はカタログ送信に進まない。リトライは無効。出力の `prepared.json` と `comparison.json` は別に保存する。生成物はoutputs配下で管理し、gitへカタログやベクトルを追加しない。

採否は各検索の上位5冊を人手で「目的に合う／一部合う／無関係」と評価する。完全一致の維持、フィルター違反ゼロ、無意味検索の扱い、冷キャッシュ・温キャッシュの待ち時間を合わせて判断する。現段階で検索精度が上がったとは判断しない。

参考: [Embed API](https://docs.aws.amazon.com/bedrock/latest/userguide/model-parameters-embed-v3.html)、[Rerank API](https://docs.aws.amazon.com/bedrock/latest/userguide/rerank-use.html)、[料金](https://aws.amazon.com/bedrock/pricing/)。

## 小規模実測（2026-09-28、ユーザー承認範囲30冊・3検索）

その後の呼び出しは成功。アカウント全体の状態変更は確認していないが、Cohere Embed Multilingual v3とRerank 3.5は実行できた。全カタログへ拡大せず、Python8冊・UIデザイン4冊・英語学習8冊とその他10冊の計30冊で比較した。すべて内容紹介のある本を選択。関連本を含めた意図的なサンプルなので、全蔵書での精度を示す試験ではない。

結果ファイル: `outputs/semantic-small/comparison.json`（対象IDも記録）。埋め込み33呼び出し（30冊＋3検索）、Rerank3呼び出し。入力データは既存カタログのみ。新規AWSリソースやUIへの反映はない。

|検索文|意味検索の1位|検索時間|Rerank追加時間|
|---|---|---:|---:|
|Pythonでデータを分析したい|Pythonによるあたらしいデータ分析の教科書|5ms（検索文ベクトルはプローブ時のキャッシュ）|477ms|
|使いやすいアプリの画面を設計したい|UIデザインの教科書|199ms|749ms|
|英語を文法からやり直したい|シャーロック・ホームズから始める英文解釈|159ms|342ms|

ローカルのAND/別名キーワード比較では3件とも0件。実UIの誤字補正を含む比較ではない。意味検索は3件とも分野に合う本を上位に出したが、英語の「やり直し」への適合は十分でなく、書誌だけで初心者向けとは断定できない。RerankでPythonの上位3冊は変わらず、UIは2位と3位が逆転、英語は3位が「イギリス英語音声学」から「確かな英語の力を育てる」に変わった。英語の後者も教える側の本かもしれず、順位変化を精度向上と同一視しない。

仮説: 自然文から候補を拾うにはベクトルの効果がありそう。Rerank常時実行の効果はこの3件では未確定で、追加遅延に見合うか要検証。最近傍下位には無関係な本も混ざるため、関連性閾値の評価が公開検索への次の条件。各時間は1回の測定であり本番性能の保証ではない。

## 検索精度の点検

結果の有無だけでなく、上位5冊の内容紹介を読み、検索意図との一致を確認した。評価者はアシスタントであり、ランキングを見た後の暫定判定。ブラインド評価や利用者評価ではない。

- Pythonのデータ分析: 意味検索・Rerankとも上位3冊は、データ取得・加工・可視化、実践分析、Pythonによる統計分析を扱い、目的に直接合う。4位以下は一般的なPython入門・機械学習などに広がる。
- アプリ画面の使いやすい設計: 両方式の上位3冊はUI設計そのもの。4位は音声UIで画面設計とはずれ、5位はPython一般書。Rerankはこの混入を解消しない。
- 英語を文法からやり直す: 1位は英文精読と構文・文法コラム、2位は英語史から文法を解説する本。一部関連はあるが、基礎からやり直す教材である根拠は不足。Rerank3位「確かな英語の力を育てる」は紹介文が明記する通り先生向けであり、学習者の目的に合わない。順位変更を改善とは評価しない。

さらに稼働中のローカルAPI `/api/books/search` へ6検索を送り、現行挙動を確認した。自然文3件は全て0件。一方で短いキーワードなら「Python データ分析」9件、「UI デザイン」4件、「英文法」10件。Pythonの上位には分析教材が並び、UI上位3冊は意味検索と同じ3冊だった。結果は `outputs/semantic-small/current-api-baseline.json`。APIは全カタログ、意味検索は30冊のため、これを同一条件の精度勝負として集計しない。フロントエンドの誤字補正はこのAPI確認に含まない。

結論: 自然文で候補を取得する能力については、このサンプル内で改善を確認。適切なキーワードを入力した既存検索より順位精度が高い証拠はまだない。Rerank追加の利益も確認できない。次の比較は同じ候補集合・同じ入力で行い、自然文だけでなく短いキーワード、既知の書名、誤字、該当なしを含める。評価前に関連本と対象読者を固定し、上位の目的適合率と無関係結果の混入を測る。英語のやり直し教材をサンプルに含めず「正解を拾えない」と結論しない。

## 短いキーワードでの採否（2026-09-28）

ユーザーが確認したいのは自然文処理ではなく、短い語が書名・紹介文に直接含まれなくても関連本を取得できるか。`scripts/evaluate_keyword_vectors.py` で既存の30冊のベクトルを再利用し、10検索語のみ追加送信。Rerankは呼んでいない。結果: `outputs/semantic-small/keyword-comparison.json`。

検索前に、内容紹介に基づいて期待する本IDと比較用の言い換えを固定した。判定はアシスタントによる暫定評価。関連書籍が存在するように選んだ小標本であり、独立した評価集合ではない。

|検索語（対象の書名・紹介文に存在しない語）|ベクトル1位|比較用の関連語|
|---|---|---|
|ユーザビリティ|UIデザインの教科書|UIデザイン|
|データクレンジング|Python実践データ分析100本ノック|データ分析|
|スタートアップ|会社を老化させない経営者の極意|起業|
|リクルーティング|採用の問題解決の本|採用|
|英文読解|シャーロック・ホームズから始める英文解釈|英文解釈|
|音声操作|デザイニング・ボイスユーザーインターフェース|ボイスユーザーインターフェース|

この6検索は同じ30冊のキーワード検索では0件。ベクトルでは6件とも1位が事前の期待IDに含まれた。ただし上位3冊では18枠中10枠だけが期待IDで、周辺分野まで広がる。比較用の関連語を手で与えても6検索全てで期待本を少なくとも1冊取得できる。これは辞書整備済みなら可能という証拠であり、既存システムで自動的に実現済みという意味ではない。「データクレンジング→データ分析」など上位概念への拡張は厳密な同義語ではなく、全蔵書への適用はノイズ増加のおそれがある。辞書も今回の結果だけで追加しない。

対照として「発音」「Python」を確認し、標本に該当本がない「離乳食」と無意味文字列も検索した。閾値なしのベクトル順位では、離乳食の1位が起業の本（cosine 0.4702）、無意味文字列は妄想講義（0.4505）。一方、データクレンジングの正しい1位は0.4612。単一の類似度閾値を上げるだけでは、この誤検出と正解を同時に区別できない。

検索文の埋め込みは全10件でキャッシュなし、中央値約136ms、最初の1件は618ms、残り9件は114〜203ms。ローカル30冊のコサイン計算は約1〜3ms。キーワード＋手動関連語照合は同じローカル配列で約0.4〜1ms（API比較ではない）。本番の全蔵書・同時アクセス性能は未測定。初回の遅さの原因は切り分けておらず、コールドスタートとは断定しない。

**採否: 今回は通常検索へベクトルもRerankも導入しない。** 未知語から候補を拾える点は確認できたが、無関係結果の抑制と追加待ち時間を考えると、速い通常検索に常時組み込む価値は未証明。現在のキーワード・既存別名検索と「もしかして」補正を維持する。今回の試作は将来のAI検索で候補を集める手段として保留する。全カタログの埋め込み生成、追加の辞書整備、検索画面への組み込みには進まない。
