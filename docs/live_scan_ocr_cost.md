# ライブスキャンのOCRコスト制御

ライブ中はブラウザで15fpsを上限にフレームを評価し、ブレ、前回との差分、3fpsの送信上限を通ったJPEGだけをセッションへ残す。開始・候補フレーム送信・確定・キャンセルはローカルGo APIとAWS APIで同じ状態遷移（`collecting -> pending` または `canceled`）にする。

確定前はYOLO・Gemini・棚候補更新を実行しない。これはGemini課金を止めるための境界であり、候補JPEGの保存自体は課金対象ではない。現段階では既存の単発アップロード経路を互換で残しているため、ライブセッションだけがこの境界を使う。

AWS YOLO worker は確定時の `image_keys` を一つのジョブとして集約する。既存の品質ゲート後、同一セッション内では知覚ハッシュ、再スキャンでは棚ID・正規化位置・知覚ハッシュを照合する。重複cropは `skipped_duplicate_crop` と既存OCR参照を保存し、Geminiキューへ送らない。永続フィンガープリントはGemini成功時だけ更新し、失敗や空結果で将来の再OCRを抑止しない。

棚候補はlookup workerが一括カタログを作る段階だけで更新する。重複参照cropは新しい棚観測として数えない。キャンセル済みS3フレームは削除し、放置された `live/` フレームも7日で期限切れにする。

Geminiが個別cropで失敗した場合は、そのcropに `ocr_error` を残して他のcropを完了させ、ジョブは結果画面まで進める。失敗cropのフィンガープリントは保存しないため、次回スキャンでは再度OCR対象になる。YOLOや集約処理自体が失敗した場合はジョブ全体を `failed` にする。
