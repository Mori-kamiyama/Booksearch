# 意味検索の軽量採点と候補除外

## 方針

ベクトル検索の上位50冊を、書名・著者・確認済み紹介文で再採点する。追加のモデルAPIは呼ばず、通常検索の結果には適用しない。候補を5冊に埋めず、条件を満たした最大5冊だけ返す。

採用条件はコサイン類似度0.50以上、検索の内容語の60%以上に書誌上の根拠があること。日本語の内容語は既存のKagome/IPADICを使い、連続する名詞を複合語として扱う。「離乳食」を「食」だけで通さない。「本」「方法」「初心者」などは関連性の根拠に数えない。

データクレンジング→データ前処理、英文読解→英文解釈などは小さな同義語辞書で補う。辞書で認識した概念と英字の指定語は、候補側にも必須とする。C++とC/C#、UIとbuildingなどの文字列内の偶然一致を区別する。説明文は既存の `fetch_status='matched'` のものだけを使用し、説明がない場合は書名と著者で判断する。

通過した候補の点数は `cosine + 0.12 × 書名の一致率 + 0.06 × 全体の一致率`。初心者・入門の希望と既知のbeginnerが合えば0.03を足す。除外判定は点数とは独立し、加点で低類似度・根拠なしの本を復活させない。条件と除外IDは従来どおりベクトル計算前に適用する。

## 検証と限界

`uv run scripts/evaluate_semantic_rules.py` は4,202冊の索引・対応DBと保存済み検索ベクトルを使い、実際のGoの採点関数を評価する。索引とDBのSHA256を確認し、未保存の検索ベクトルはエラーにする。AWSやRerankは呼ばない。出力はGit管理外の `outputs/semantic-rules/`。

12検索の回帰確認では、離乳食・無意味文字列・ワープエンジン修理・ドラゴン飼育は0件。残る8検索は候補を維持した。データクレンジングは前処理本2冊、使いやすいアプリの画面設計はUI教科書とインタフェースデザイン本2冊になった。後者に混ざったVisual C++のアプリ実装本とPythonのソフトウェアアーキテクチャ本は、明示された使いやすさ・画面の両方を裏付けられず除外された。採点関数だけのローカル1回計測は約0.004〜1.9ms。ベクトル取得・SQL・通信を含む速度ではない。

これは正解ラベルを持つ精度評価ではなく、小規模な回帰確認。0.50と60%は暫定値であり、同義語辞書にない言い換え、書誌が乏しい本、複合語の表記差は取りこぼす。紹介文に関連語があるだけで本全体が目的に合うとは限らない。たとえば採用検索には採用試験向けプログラミング本がまだ残る。完全な無関係候補の排除を保証するものではない。

まず「最近傍だから必ず表示する」挙動を止める。検索ログや具体的な失敗例が得られたら、未評価の検索も含めて辞書・閾値を調整する。現在の12例だけに合わせて大型モデルや学習基盤を追加しない。
