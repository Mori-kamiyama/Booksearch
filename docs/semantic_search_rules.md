# 意味検索の軽量採点と候補除外

## 方針

ベクトル検索の上位50冊を、書名・著者・確認済み紹介文で再採点する。追加のモデルAPIは呼ばず、通常検索の結果には適用しない。候補を5冊に埋めず、条件を満たした最大5冊だけ返す。

採用条件はコサイン類似度0.50以上、検索の内容語の60%以上に書誌上の根拠があること。日本語の内容語は既存のKagome/IPADICを使い、連続する名詞を複合語として扱う。「離乳食」を「食」だけで通さない。「本」「方法」「初心者」などは関連性の根拠に数えない。

データクレンジング→データ前処理、英文読解→英文解釈などは小さな同義語辞書で補う。辞書で認識した概念と英字の指定語は、候補側にも必須とする。C++とC/C#、UIとbuildingなどの文字列内の偶然一致を区別する。説明文は既存の `fetch_status='matched'` のものだけを使用し、説明がない場合は書名と著者で判断する。

通過した候補の点数は `cosine + 0.12 × 書名の一致率 + 0.06 × 全体の一致率`。初心者・入門の希望と既知のbeginnerが合えば0.03を足す。除外判定は点数とは独立し、加点で低類似度・根拠なしの本を復活させない。条件と除外IDは従来どおりベクトル計算前に適用する。

`uv run scripts/evaluate_semantic_rules.py` は4,202冊の索引・対応DBと保存済み検索ベクトルを使い、実際のGoの採点関数を評価する。索引とDBのSHA256を確認し、未保存の検索ベクトルはエラーにする。AWSやRerankは呼ばない。出力はGit管理外の `outputs/semantic-rules/`。

12検索の回帰確認では、離乳食・無意味文字列・ワープエンジン修理・ドラゴン飼育は0件。残る8検索は候補を維持した。データクレンジングは前処理本2冊、使いやすいアプリの画面設計はUI教科書とインタフェースデザイン本2冊になった。後者に混ざったVisual C++のアプリ実装本とPythonのソフトウェアアーキテクチャ本は、明示された使いやすさ・画面の両方を裏付けられず除外された。採点関数だけのローカル1回計測は約0.004〜1.9ms。ベクトル取得・SQL・通信を含む速度ではない。

これは正解ラベルを持つ精度評価ではなく、小規模な回帰確認。0.50と60%は暫定値であり、同義語辞書にない言い換え、書誌が乏しい本、複合語の表記差は取りこぼす。紹介文に関連語があるだけで本全体が目的に合うとは限らない。たとえば採用検索には採用試験向けプログラミング本がまだ残る。完全な無関係候補の排除を保証するものではない。

まず「最近傍だから必ず表示する」挙動を止める。検索ログや具体的な失敗例が得られたら、未評価の検索も含めて辞書・閾値を調整する。現在の12例だけに合わせて大型モデルや学習基盤を追加しない。

## 数値だけ返す判定とJevの候補

ユーザーの提案でGeminiの選別出力を20候補の順番に対応する整数配列へ変更する試作を実施。0=無関係・根拠不足、1=同分野だが対象や用途が違う、2=関連基礎書、3=直接該当。2以上を最大5冊表示し、同点は元のベクトル順位を維持する。数値は確率ではない。固定配列長・整数・範囲を検証し、理由文と候補IDの生成を省く。minimal thinkingは理由付き試作でも設定済みであり、今回新しく効いた変更とは扱わない。

同じ検索意図・上位20候補でストリーミングを計測。各条件1回、理由付き→数値のみの判定完了時間は、ぷろぐらみんぐ入門3,683→1,164ms、LLM2,151→1,207ms、離乳食951→1,294ms。最初の非空テキスト受信は順に2,539→1,164ms、818→1,101ms、787→1,225ms。TTFTが短いほど必ず判定全体も速いわけではなく、出力終了までの時間を測る必要がある。プランナー・埋め込み・APIの処理はこの計測に含まない。モデルの内部計算だけでなく通信・サービス負荷・クライアント初回接続も含み、固定順序の単発比較なので平均やp95の改善率ではない。数値版は候補IDも入力から省いている。

紹介文を700文字から300文字へ削った数値版は1,237/1,145/954ms。入力トークンはそれぞれ6,652→3,477、5,792→3,193、4,466→2,833となったが、待ち時間は一貫して改善せず、LLMで直接該当扱いの本が増えた。初期採用では極端な書誌切り詰めを急がない。数値版も入門書を残し離乳食を0件にできたが、BERT本を直接該当にする問題は残る。理由文を省く変更は速度対策であり、精度改善を示したものではない。試作・結果は `outputs/semantic-llm-trial/numeric_trial.py`、`numeric_report.json`。本番は未変更。

Jevは[TypeSafeの公式ドキュメント](https://docs.typesafe.ai/introduction)で確認した。状態に対する複数の型付き質問を1回で評価でき、Scoreは段階別確率とconfidenceを返す。候補ごとの目的適合性を質問する構成に適しているという仮説。公式の速度値は米国西海岸からの測定とされ、東京からの速度・日本語書誌の精度・書籍検索における確率校正は未検証。今回JevのAPIは呼び出していない。新しい認証や依存を導入せず、まず既存Geminiの数値版で評価基準を揃える。

## 最終方針：ベクトル順位と軽いトリアージ

ユーザーがモデルによるrerankを取りやめ、軽量なルールだけ少し残す方針を指定した。Gemini/Jevは導入しない。書名一致・内容語網羅・入門レベルの加点を廃止し、通過した候補はコサイン降順、同点はID昇順とする。内容語60%一致の必須条件も外す。

暫定トリアージは、非有限値・コサイン0.50未満を除外し、0.60未満の候補には内容語または既存の別名の一致を最低1つ要求する。0.60以上は自然言語の文字一致がなくても通過できる。明示されたLatin識別子（Python/C++/LLM/UIなど）については、単語境界・既存の別名で裏付けを求める。自然言語の概念別名は必須一致にしない。内容語のない一般語だけの検索は補完しない。モデル追加・検索時API呼び出し追加・索引更新はない。

両方のGo実装の全テストが成功。同じ4,202冊の索引と保存済み埋め込みによる14例は、正例10検索の候補を維持し、離乳食・無意味文字列・ワープエンジン修理・ドラゴン飼育は0件。ルール単体の1回計測は約0.01〜2.5ms（検索全体の時間ではない）。評価結果は `outputs/semantic-light-triage/`。自然言語の用途を厳密には判定しないため、画面設計検索にはAndroid/Visual C++のアプリ実装本も通過する。これは取りこぼしを減らすために採ったトレードオフであり、無関係候補の完全排除や精度改善は保証しない。0.50/0.60もモデルと蔵書に対する暫定値。本番はこの試作時点では変更していない。
