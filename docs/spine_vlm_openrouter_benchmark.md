# 背表紙文字起こし向け小型 VLM の OpenRouter 比較

実施日: 2026-09-23

## 結論

- 第一候補は `qwen/qwen3.5-9b`。`reasoning.enabled=false` を指定すると、8枚すべてで有効な JSON を返し、書名も8/8枚で特定できた。今回の実測費用から1500枚を概算すると約 `$0.12`。
- 速度と扱いやすさを優先するなら `qwen/qwen3-vl-8b-instruct`。8/8枚で有効な JSON、書名も8/8枚で特定でき、平均3.85秒だった。1500枚の概算は約 `$0.27`。
- `mistralai/ministral-3b-2512` は最安だが、日本語OCRの誤字と不正JSONが多い。教師データ作成には向かない。
- `openai/gpt-4o-mini` は今回の細長い画像では画像入力トークンが大きく、Qwenよりかなり高価だった。精度もQwenを上回らなかった。
- `google/gemma-3-4b-it` は8件すべてOpenRouterの上流プロバイダが429を返し、比較不能だった。

したがって、1500冊について基盤モデルを一から作るのではなく、Qwen 3.5 9Bで仮ラベルを作り、人手で修正したデータを将来のLoRA用データにするのが現実的。現時点ではAPI推論だけでも十分安い。

## 条件

- 入力: YOLO OBBで1冊ずつ切り出し、射影補正した背表紙8枚
- 内訳: 英語2枚、日本語6枚。短い題名、長い縦書き、英日混在を含む
- 出力: `transcription`, `title`, `author`, `call_number`, `confidence` のJSON
- 温度: 0
- 出力上限: 300トークン
- 同時実行数: 4
- 費用はOpenRouterレスポンスの `usage.cost` を集計
- 判定: 自動完全一致に加え、転記全文から書籍を特定できるかを目視判定

画像はOpenRouter経由で各モデルの推論プロバイダへ送信した。

## 結果

| モデル | 書名を特定 | 有効JSON | 平均時間 | 8枚の実費 | 1500枚概算 |
|---|---:|---:|---:|---:|---:|
| Qwen 3.5 9B、推論OFF | 8/8 | 8/8 | 7.25秒 | $0.000652 | 約$0.12 |
| Qwen3-VL 8B Instruct | 8/8 | 8/8 | 3.85秒 | $0.001418 | 約$0.27 |
| GPT-4o mini | 6/8 | 7/8（1件タイムアウト） | 12.57秒 | $0.021008（成功7件） | 約$4.50 |
| Ministral 3B | 3/8 | 4/8 | 5.95秒 | $0.000595 | 約$0.11 |
| Gemma 3 4B | 未評価 | 0/8 | - | $0 | - |

1500枚概算は今回と同程度の画像サイズを前提にした単純比例。GPT-4o miniだけは成功7件の平均単価を使った。

### Qwen 3.5 9B の注意点

既定の推論ありでは、画像の読み取り自体は良好だったが、内部推論が300トークンを使い切り、4/8件で最終JSONが空になった。`reasoning: {"enabled": false}` を指定すると8/8件で正常化し、費用も8枚で `$0.000652` まで下がった。この指定は実運用で必須。

### 書名フィールドの評価について

自動完全一致は両Qwenとも5/8だったが、これはOCR失敗をそのまま表していない。

- `ANSEL ADAMS 400 PHOTOGRAPHS` に対し、モデルは著者を分離して `title="400 PHOTOGRAPHS"` とした。
- `Head First デザインパターン 第2版` に対し、`Head First` と `第2版` は全文転記に含めつつ、`title="デザインパターン"` とした。
- `地方における戦後都市計画` に対し、Qwen 3.5は副題までtitleに含めた。

つまり8枚とも必要な書名文字は読めている。学習・評価では `title` の完全一致だけでなく、全文転記の文字誤り率（CER）と、書誌DBへの照合成功率を使うべき。

## 観察した失敗

- 小さい著者名や請求記号は、正しい場合もあるが誤読・補完が混ざる。別の煙試験ではQwen3-VL 8Bが著者名を誤って補った。
- モデル自身の `confidence` は誤読時でも1.0になることがあり、採用判定には使えない。
- Ministral 3Bは文字列中に生の改行を入れた不正JSONを返すことがある。
- GPT-4o miniは同じ切り出しでも入力トークンが非常に多くなった。
- Gemma 3 4Bはモデル品質以前に、現在割り当てられた上流プロバイダの混雑で利用できなかった。

## 実装方針

まずは次の最小構成がよい。

1. 棚Crop YOLO
2. Bookfinder系YOLO OBBで背表紙分割・射影補正
3. Qwen 3.5 9B、推論OFFで全文転記
4. JSON不正または空文字だけQwen3-VL 8Bへフォールバック
5. ISBN/蔵書目録候補との文字列照合
6. 照合できないものだけ人手確認

書名・シリーズ・版・副題の境界は曖昧なので、最初は `transcription` を正として保存する。構造化フィールドは後処理で分ける方が安全。

1500冊の修正版が集まった後に、Qwen系の小型VLMへLoRAする価値を再評価する。1500件は狭い背表紙OCRへの適応には使えるが、汎用VLMを一から学習する量ではない。

## 再実行

比較スクリプト: `benchmark/openrouter_spine_vlm.py`

サンプル定義: `benchmark/spine_vlm_samples.json`

uv run python benchmark/openrouter_spine_vlm.py \

## 追試: 2B以下のローカルモデル候補

2026-09-23時点では次の候補がある。

| 候補 | 規模 | 日本語OCRとの相性 | 判断 |
|---|---:|---|---|
| Qwen3.5-2B | 2B | 公式CC-OCRがQwen3-VL-2Bより高く、多言語 | 本命 |
| Qwen3-VL-2B-Instruct | 2.13B | 32言語OCR、暗所・ぼけ・傾きも訴求 | 比較対象 |
| PaddleOCR-VL | 0.9B | 日本語を含む109言語、OCR専用 | 強い比較対象 |
| Qwen3.5-0.8B | 0.8B | 日本語対応だが容量限界が見える | 追加学習実験向け |
| SmolVLM2-500M | 0.5B | 公式モデルカード上の主言語は英語 | 今回は優先度低 |
| SmolVLM2-256M | 0.256B | 同上。極小だが日本語OCRを1500件で覚えさせるのは厳しい | 見送り寄り |

Qwen3.5の公式評価ではCC-OCRが2Bで `72.9/75.8`、0.8Bで `63.2/66.7`。モデルを小さくした際のOCR性能低下が確認できる。一方、PaddleOCR-VLは汎用チャット能力を削ってOCRへ寄せた0.9Bなので、背表紙用途では必ず比較する価値がある。

### Qwen3.5-0.8B 4bitのローカル実測

既にローカルにあった `mlx-community/Qwen3.5-0.8B-4bit` を同じ8枚で実行した。

- 量子化モデル容量: 約622MB
- ピークメモリ: 約1.64GB
- モデルをロードした後の処理時間: 1枚1.4〜4.9秒
- 明瞭な短い背表紙は読めた
- 難しい4枚では欠落、幻読、同一文字の反復、空に近い出力が発生

速度とメモリは非常によいが、素の4bit版をそのまま本番へ入れる品質ではない。0.8Bを採用するなら、背表紙データでの追加学習と、出力反復を検知して上位モデルへ送るフォールバックが必要。

Qwen3.5-2Bの4bit版は約1.74GB。取得を試みたがHugging Faceからのダウンロードが停滞したため、この時点では同一8枚の実測を完了していない。

## 前処理と学習データの方針

学習データには暗所、色かぶり、低コントラスト、反射、軽いぼけ、JPEG劣化を混ぜる。ただし、すべてを劣化画像にせず、実分布に近い正常画像を過半数残す。

推論時は次の決定的な前処理だけにする。

1. EXIF方向とOBB射影補正
2. 細すぎるCropを拡大し、文字の横幅を確保
3. 輝度チャンネルだけに弱いパーセンタイル補正またはガンマ補正
4. 元画像は必ず保存

強いCLAHE、二値化、過剰なシャープ化、RGBチャンネル別の強い補正は文字形状や色境界を壊すため既定処理にしない。学習時には実運用と同じ軽補正済み画像を中心にし、一部だけ無補正・劣化Augmentationを混ぜる。

## AWSへの載せ方

- 現在の通常LambdaにはGPUがない。0.8BをCPU量子化で動かす実験は可能だが、コールドスタートと推論時間を測る必要がある。
- 2BまたはPaddleOCR-VL 0.9Bの安定運用は、SageMaker Asynchronous InferenceかGPU付きEC2/ECSが素直。
- SageMaker Asynchronous Inferenceはキュー処理と0台へのスケールダウンが可能なので、現在のSQSベース構成と相性がよい。
- G6のfractional GPUは最小3GB VRAMから利用できるため、0.8B/0.9B量子化モデルの候補になる。2Bは実測後に必要VRAMを決める。

OCRだけを最小化する場合は、PP-OCRv6の日本語対応認識器も別系統で比較する。文字行の検出と読順復元は必要になるが、認識器は1.5M〜34.5Mパラメータで、VLMよりはるかに軽い。

## 現在のAWS構成を前提にした選定

現状のOCR Workerは、SQSからCropを1件ずつ受け取るARM64 Lambdaで、メモリ512MB・タイムアウト120秒。これは外部API呼び出しには適しているが、0.8B以上のVLMをローカル推論する構成ではない。Lambdaコンテナへ無理に載せると、CPU推論、モデル展開、コールドスタートが支配的になる。

この条件での第一候補は `PaddlePaddle/PaddleOCR-VL` 0.9Bとする。

理由:

- Qwen3.5-0.8Bとほぼ同規模だが、汎用VLMではなくOCRへ容量を集中している
- 日本語を含む109言語対応
- 動的解像度の視覚エンコーダを持つ
- vLLM対応でGPUサービングしやすい
- Apache-2.0
- Qwen3.5-2Bより軽く、同時処理数を増やしやすい

構成案:

1. YOLO Lambdaが背表紙CropをS3へ保存
2. OCR要求LambdaがSageMaker Asynchronous InferenceへS3 URIを渡す
3. PaddleOCR-VL 0.9Bが複数Cropをまとめて処理
4. 完了通知をSNS/SQSで受け、DynamoDBへ結果を保存
5. 空出力、反復、蔵書DB不一致だけ既存Geminiへフォールバック

SageMaker Asyncは0台まで縮退できるため、断続的な棚スキャンと相性がよい。現在のようにUI側がジョブ完了をポーリングする設計なら、GPU起動待ちも扱える。

ただし、1冊ごとにSageMakerを呼ぶより、1棚ジョブのCropを8〜32枚程度まとめて1リクエストにした方が、モデル起動・通信・バッチ推論を効率化できる。現在の1Crop＝1 SQSメッセージは、完了更新用には残しても、GPUへの入力はジョブ単位にまとめる。

選定順位は次の通り。

1. AWS本番既定: PaddleOCR-VL 0.9B
2. 難例・将来のLoRA比較: Qwen3.5-2B
3. 超軽量研究枠: Qwen3.5-0.8B
4. CPU Lambdaを最優先する別案: PP-OCRv6 small/medium

最終確定前に、同じ背表紙50枚でPaddleOCR-VL 0.9BとQwen3.5-2Bを比較する。PaddleOCR-VLの縦書き読順が弱い場合だけ、Qwen3.5-2Bを本番既定へ繰り上げる。
