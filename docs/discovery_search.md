# 検索・発見機能の実装方針とローカル検証

## 合意した順序

検索候補 → 著者/ジャンル/ページ数/レベルの絞り込み → 関連本の高度化 → Agentic検索 → 根拠付き要約。
今週のおすすめは現在の発見性・初期HTML表示を維持する。推薦改善の中心は詳細画面の関連本。

## 今回の実装

- 書名・著者・テーマの候補を静的索引からブラウザ内で検索する。250ms debounce、最大6候補、完全一致→前方一致→部分一致。全半角・英字大小文字・かなを正規化。IME・上下キー・Enter・Escape・タップ、遅い取得結果の混入防止を実装。
- 索引の取得は検索入力時、または絞り込み画面を開くとき。ページ内で共有し、失敗しても通常検索は利用可能。読みがない漢字書名のかな検索は未対応。
- テーマ候補は検索文字列へ置換せずtopicフィルタで遷移。著者は蔵書の著者表記全体を一致条件とする。共著者の個別人物同定は未実装。
- GoのローカルAPI・AWS APIに同じフィルタ実装を追加。SQLパラメータで条件を適用し、件数計算後にページ分割。条件不正は400、テーマ索引未配置はエラーにし、条件を無視して広い結果を返さない。
- URLにauthor/topic/min_pages/max_pages/levelを保存。詳細から戻る際の条件・スクロールを復元。解除操作を提供。
- 配信用DBと候補索引を同じ生成処理から作る。元DBは変更しない。AWSのprepare_assetsにも組み込み、両方を同時更新する。

## 現物データと限界

調査対象はローカルの `aws/functions/go_api/library.db`。4,202冊、book_metadataは0件。ページ数・内容紹介・レベル・読みが十分あるという前提は置かない。本番DBを調査した結果ではない。

候補索引375,867 bytes、gzip 116,219 bytes。端末実測の速度は未評価。

大分類は既存分類番号から導出。細かいテーマは初期ルール5種（C言語・ブルータリズム・英語学習・Python・デザイン）の書名一致に限定し、book_topicsに根拠文字列を保持する。自由テーマの意味判定や網羅的なジャンル分類は未実装。C言語17冊、英語学習62冊、Python16冊、デザイン142冊。ブルータリズムは書名一致0件なので候補に出さない。0件は未所蔵の証明ではない。

ページ数はmatchedの書誌メタデータだけから取り込む。レベルは根拠がないのでNULLを維持。現データでは両フィルタを準備中として無効化する。後から書誌補完とレベル判定・確認の仕組みを追加する必要がある。これらを機能完成扱いにしない。

## Agentic検索のローカル実行部分

`scripts/discovery_agent.py` は意思決定関数を差し替えられる読み取り専用の実行ループ。search / inspect / facets / finishを用意。結果0件を見て別の検索へ進むテストを作った。

- 必須条件は実行側で保持し、plannerにページ数等の上書き操作を渡さない。
- 書籍詳細を確認したIDだけを最終結果に採用。根拠はDBから返し、plannerが作った推薦理由をそのまま事実として公開しない。
- 最大6手（設定上限12手）で終了。未完了時はbudget_exhaustedとし、成功を装わない。
- **LLM、自然文からの条件抽出、意味検索、Web UIへの接続は未実装。** モデル呼び出しのtimeoutはplanner adapter側で必要。現在のテストはscripted plannerで、AI検索の品質評価ではない。

## 再現手順

```sh
uv run --no-project python scripts/build_discovery_index.py \
  --db aws/functions/go_api/library.db \
  --output-db /tmp/booksearch-discovery/library.db \
  --output-index frontend/public/search-index.json
cd backend
go run . --host 127.0.0.1 --port 18089 --library-db /tmp/booksearch-discovery/library.db
```

API確認: `/api/books/search?topic=c-language&limit=2` が全17冊中2冊を返した。フロントはそのAPIへ接続して確認する必要がある（Vite既定proxyは8080）。

配信は **索引付きDB/API → 同じ索引のfrontend → 同じコードで再ビルドしたhome publisher** の順で整合を取る。旧APIのまま新UIだけを配信しない。今回は本番未反映。

## 検証結果

- フロント単体49件成功、両Goモジュールの全テスト成功。フィルタ後の件数とページ送り、不正条件、SQL文字列の入力、未配置索引を検証。
- 生成器・Agent実行部分3件成功。元DB不変、曖昧な書誌を除外、条件を保持した再検索、架空ID拒否、回数上限を検証。
- UI回帰は全体実行で58/66成功。残る8件は検索フォーム以外の入力欄追加による既存テストselectorの曖昧さだった。selectorを名前で指定するよう更新後、該当ファイル44件すべて成功。既存の詳細画面の変更に伴うスキャンボタン名もテストと一致させた。
- 実データのローカルAPIでC言語17冊を確認。モバイル幅390pxのChromiumで表示・タップを確認。候補検索関数をローカルChromiumで50回測定しp95 8.9ms、最大15ms。通信・250ms debounceは含まない。CPUスロットルなしで、実スマホ性能を保証する計測ではない。
- 内容に基づく関連本、LLM検索、要約の品質を確認した結果ではない。
- 最後のUI調整後、候補/絞り込み/ページ送り/ホーム事前描画の11件も成功。ページ数・レベルは折りたたみ内に置き、データ未収録を明示する。
- 配信時は `/search-index.json` も更新・キャッシュ無効化の対象に含める。実装第1弾はローカルでレビュー可能な状態までとし、本番反映・LLM接続・書誌補完は残す。

## フィルターUIの見直し（2026-09-28）

ユーザーの追加指定により著者フィルターをUIから撤去。書名/著者の通常検索・入力候補は維持する。旧author URLは条件を外して正規化し、見えないフィルターを残さない。APIの著者パラメータは互換性のため維持する。

検索結果の常設フォームをフィルターボタン＋適用中条件のチップに変更。フローティングdialogで編集し、適用するまで検索条件は変えない。閉じる/Escape/背景タップで下書きを破棄し、ボタンへフォーカスを戻す。

ジャンルは広い分類、テーマは具体的な対象に分離。粒度の大きい「デザイン」テーマをタイポグラフィ/UIデザイン/グラフィックデザインの書名ルールへ置換。ジャンルとテーマはSQLでAND条件にする。テーマに属する実際の本の分類から対応ジャンルを生成し、選択ジャンルに該当するテーマだけ表示する。ジャンル変更で不整合になるテーマは下書きから外す。

320px/1024pxで表示幅、未適用状態、適用、キャンセル、Escape、背景クリック、条件解除・URL復元を確認。候補/ページ送り関連8件とパネル2件成功。フロント単体49件、両Goモジュール、生成器/Agent3件成功。本番未反映。
