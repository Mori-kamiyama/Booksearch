# 「もしかして」の日本語補正

## 問題と方針

従来は書名・読み・テーマの編集距離で並べた先頭候補を、同点でも文字順で自動採用していた。ジャンルの別名に近い入力をジャンル名全体へ変換する問題もあった。例: `デザiン` を `デザイン・アート` にすると、通常検索では欲しい本が出ない可能性がある。

2026-10-03の改善では、ジャンルの別名の誤字は検索できる別名自身へ戻す。`デザiン`、`デザイソ`、`デザインン` → `デザイン` を現行4,202冊のブラウザ索引で確認。全半角・英字大小・ひらがな/カタカナの正規化と、文字の挿入・削除・置換・隣接転置を使う。新しいモデルや外部APIは追加しない。

同じ最小編集距離に複数の補正語があるときは、自動再検索せず最大3候補を「もしかして…」として提示する。同点判定は候補を3件に切る前に行う。表示の文字順を信頼度とみなさない。

複数語は最大4語、誤字らしい1語だけを修正し、残りを保持する。補正後の全語が同じ蔵書の書名・著者・確認済み読みに含まれることを確認する。語彙は既存テーマ・別名・書名と、書名の区切りや英字から抽出した語。日本語の任意の部分文字列や同義語を新規生成しない。著者名は補正対象にせず、文脈の確認だけに用いる。

3文字のかな入力にも候補を出せるが自動採用しない。漢字の置換がある同じ長さの入力（`科学入門` → `化学入門` など）も選択式にする。ISBN、C++/C#などの記号つき識別子、2文字以下、80文字超、既知の検索語を近い別語へ書き換えない。絞り込み・元の検索語での再検索・誤字補正後のページ送りは維持する。

## 仮説と限界

文字順での同点解消を止め、ジャンル別名を検索語として扱うことで、誤補正と補正後0件を減らせると考える。これは文字列に基づく保守的な規則であり、利用者の意図を理解した確率ではない。実例と人工的な対照例での動作確認を、全体の検索精度向上率として扱わない。

読みのない漢字の読み間違い、区切りのない長い日本語書名の途中の誤字、複数語が同時に間違っている入力は十分に扱えない。異なる長さの漢字混じり語について意味の変化を完全に判別するものでもない。これらは実際の入力例を集め、誤採用率と正しい補正候補の回収を確認して改善する。

語彙生成は索引ごとにキャッシュし、入力のたびに作り直さない。通常検索0件時だけ補正し、同点候補を確認するための追加API呼び出しは行わない。自動採用する唯一の候補には通常APIで件数確認を行い、条件つきで0件なら元の検索結果を維持する。

## 検証

補正の単体テスト10件が成功。実蔵書索引での日本語例、同点候補、漢字置換、短いかな、複数語、著者・識別子の維持を含む。UIでは日本語補正4件と既存の検索候補・復帰・意味検索回帰、合計27件が成功。フロントエンドbuildも成功。検索画面の変更はローカルのみで、本番未反映。
